# Сервер и клиент · RSA, Telegram 2FA и Диффи — Хеллман с ЭЦП

Локальный учебный проект: Node.js / TypeScript, два React-интерфейса, WebSocket и PostgreSQL 17. Требуются Node.js 24+ и работающий Docker Desktop.

## Запуск в PowerShell

```powershell
Copy-Item .env.example .env
npm.cmd install
npm.cmd run db:up
npm.cmd run db:migrate
npm.cmd run dev
```

Серверный интерфейс: http://127.0.0.1:5173. Клиент: http://127.0.0.1:5174. Backend: ws://127.0.0.1:3000. PostgreSQL доступен только локально на порту 55432: стандартные порты могут использоваться другими проектами. `npm.cmd` позволяет работать без изменения политики выполнения PowerShell.

В серверном интерфейсе заполните логин, пароль и Telegram-логин, сгенерируйте RSA и добавьте пользователя. Логины приложения регистрозависимы, пробелы по краям логина удаляются. Пароли не нормализуются.

### Вход без Telegram

Если Telegram недоступен, добавьте в корневой `.env`:

```dotenv
TELEGRAM_AUTH_ENABLED=false
```

Перезапустите backend (при запуске через `npm.cmd run dev` остановите его и запустите снова). На клиенте нажмите «Продолжить»: появится поле пароля без Telegram-кода. Привязка через `/start` и токен бота в этом режиме не нужны; бот не запускается. После входа обмен DH с ЭЦП выполняется как обычно. При создании пользователя поле Telegram-логина пока остаётся обязательным.

Для возвращения проверки установите `TELEGRAM_AUTH_ENABLED=true` и перезапустите backend. По умолчанию проверка включена. Ошибка доставки кода не переключает режим автоматически; клиент не может отключить проверку своим запросом.

Без Telegram используется формула `H = SHA-256(SHA-256(пароль) + SHA-256(t))`. Сам пароль по клиентскому WebSocket при входе не передаётся. Это вход с одним фактором вместо двух.

### Настройка Telegram

1. Создайте бота командой `/newbot` у [@BotFather](https://t.me/BotFather). Добавьте выданный токен в `.env`: `TELEGRAM_BOT_TOKEN=...`. Токен используется только backend; не добавляйте его в клиент или Git.
2. Запустите backend. В консоли появится ссылка `https://t.me/<имя_бота>`. Получение сообщений работает через long polling; публичный адрес не нужен. Используйте отдельного бота без webhook и запускайте только один polling-процесс с этим токеном.
3. После создания пользователя откройте бота с указанного при регистрации Telegram-аккаунта и отправьте `/start`. Нужен username в настройках Telegram. Регистр и начальный `@` при сопоставлении не учитываются. В серверном интерфейсе появится статус «Telegram привязан».
4. В клиенте нажмите «Получить код и SHA-256(t)», затем введите пароль и шестизначный код из личного сообщения бота.

Бот не может первым начать личную переписку: пользователь должен предварительно отправить ему сообщение ([документация Telegram](https://core.telegram.org/bots)). Сохранённый `chat_id` обеспечивает дальнейшую доставку. Несколько учебных аккаунтов с одним Telegram username могут использовать один чат. Привязка другого владельца автоматически не заменяется.

Без токена, привязки или успешной отправки кода вход недоступен. При ошибке доставки проверьте подключение к интернету и блокировку бота, затем повторите запрос. После добавления токена перезапустите backend. Миграция сохраняет существующих пользователей; им также нужно выполнить `/start`.

## Лабораторная №4

После входа автоматически выполняется подписанный обмен Диффи — Хеллмана. Клиент генерирует собственную RSA-пару; сервер использует сохранённую RSA-пару вошедшего пользователя. Оба окна показывают этапы и вычисленный ключ K. Первый обмен может занять несколько минут из-за генерации p.

Формулы, протокол и демонстрация: [Диффи — Хеллман с ЭЦП](DIFFIE_HELLMAN.md).

## Устройство

Пошаговый разбор входа от создания пользователя до выхода: [Полный цикл аутентификации](AUTHENTICATION.md).

Подробный разбор кода, схемы обмена, формулы, таблицы БД и журналов: [Как устроена система](ARCHITECTURE.md).

- `apps/backend`: WebSocket-сервер, проверка входных данных, PostgreSQL и версионируемые SQL-миграции в `src/database/migrations.ts`.
- `apps/server-ui` и `apps/client`: независимые React-приложения.
- `packages/shared` и `packages/ui`: типы протокола, транспорт с переподключением и оформление.

Пароль хранится как SHA-256 от UTF-8 строки без соли по требованиям задания. Это учебная схема хранения. Открытый пароль и его хеш не выводятся в журналы. RSA-2048 генерируется средствами Node.js с e=65537. Параметры p, q, n, φ(n), e, d хранятся десятичными строками и видны только в интерфейсе сервера. Проверка d использует модуль lcm(p−1,q−1), принятый для реальных RSA-ключей. RSA используется для подписанного обмена DH после входа; шифрование сообщений не реализовано.

### Двухэтапный вход

1. Клиент отправляет `auth.challenge` с `{login}`. Сервер получает или генерирует `t`: 16 случайных байтов (128 бит). Значение хранится в PostgreSQL и повторно используется для этого пользователя ровно 24 часа, включая переподключения и перезапуски backend. При следующем запросе после истечения срока создаётся новое значение.
2. Сервер получает или генерирует число `100000–999999`, сохраняет его в БД на 10 минут и отправляет в Telegram. После успешной отправки возвращает `{challengeHash, expiresAt, telegramExpiresAt}`: хеш исходных байтов `t` и два срока ISO. Сам код и его отдельный хеш по WebSocket не передаются.
3. Клиент через Web Crypto вычисляет `H = SHA-256(SHA-256(пароль) + challengeHash + SHA-256(tgМетка))` и отправляет `auth.login` с `{proof: H}`. Три внутренних хеша — lowercase hex длиной 64 символа; `+` — склейка без разделителя. Внешний SHA-256 вычисляется от UTF-8 строки из 192 символов. Метка — шестизначная десятичная строка. Для Web Crypto открывайте клиент через localhost, 127.0.0.1 или HTTPS.
4. Сервер вычисляет тот же proof по данным БД и сравнивает через `timingSafeEqual`. Требуются challenge текущего WebSocket и действительность обоих сроков. При успехе соединение авторизуется, а challenge соединения очищается. Старый proof из двух хешей не подходит.

Код используется повторно до истечения 10 минут, включая успешные входы. Кнопка повторной отправки не продлевает срок. Истёкший код заменяется при следующем запросе; `t` живёт независимо 24 часа. Одинаковые пароль, `t` и код дают одинаковый proof — повторное использование предусмотрено лабораторной.

Оба окна показывают журнал этапов, последние 500 записей, с очисткой. `auth.log` содержит `entry` с полями `id`, `attemptId`, `time`, `side`, `step`, `message`. Клиент видит SHA-256(t), H и результат, серверное окно дополнительно t (hex) и H′. Клиентские вычисления записываются локально. Журнал не сохраняется после перезагрузки страницы. Срок t не ограничивает уже авторизованную сессию.

Управление без пароля администратора предназначено для локального использования. Backend привязан к loopback и проверяет Origin. `/ws/admin` поддерживает `rsa.generate`, `users.create`, `users.list`; `/ws/client` — `auth.challenge`, `auth.login`, `auth.me`, `auth.logout`. Запрос: `{id,type,payload}`, ответ: `{id,ok:true,data}` или `{id,ok:false,error:{code,message}}`. Событие обновления списка: `{type:"users.changed"}`. Все операции требуют payload, для операций без параметров — `{}`.

Черновик RSA и сессия живут в пределах соединения; при отключении нужно заново сгенерировать ключи или войти. При тайм-ауте создания проверьте список перед повторной попыткой. Единственный INSERT атомарно сохраняет всю учётную запись. Миграции применяются также при старте backend и защищены блокировкой от одновременного запуска.

## Проверки и остановка

ESLint настроен единым flat config для backend, React-приложений и общих пакетов: рекомендуемые правила JavaScript/TypeScript, правила React Hooks и Fast Refresh. Prettier отвечает за форматирование; `eslint-config-prettier` исключает конфликтующие правила ESLint. Общие настройки: два пробела, одинарные кавычки в JavaScript/TypeScript, точки с запятой, ширина строки 100 и окончания строк LF.

```powershell
npm.cmd run lint
npm.cmd run lint:fix
npm.cmd run format
npm.cmd run format:check
```

`lint` и `format:check` проверяют файлы без изменения и подходят для CI. `lint:fix` исправляет поддерживаемые ESLint ошибки, `format` форматирует проект. Сборки, зависимости, покрытие и служебные файлы браузера исключены; Prettier также пропускает lock-файл и файлы окружения. Для редакторов добавлен `.editorconfig`.

```powershell
npm.cmd run typecheck
npm.cmd run build
npm.cmd test
npm.cmd run db:down
```

Интеграционные тесты требуют запущенной БД, создают отдельную случайную схему и удаляют только её. Telegram в тестах подменён: токен и реальная отправка сообщений не нужны. Проверяются формула, привязка, ошибки доставки, повторные входы, граница 10 минут, перезапуск и параллельные запросы. Обычная остановка Compose сохраняет данные в именованном томе. Не используйте `down -v`, если данные нужны.

Настройки БД задаются в `.env`; при изменении пароля/порта обновите также `DATABASE_URL`. Настройки PostgreSQL инициализируют новый том, но не меняют пароль существующей БД. Vite проксирует `/ws` на порт 3000; при изменении PORT обновите target в обеих Vite-конфигурациях. Сборка интерфейсов предназначена для сервера статики с WebSocket-прокси; README-команды выше запускают локальный режим разработки.
