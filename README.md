# Сервер и клиент · RSA

Локальный учебный проект: Node.js / TypeScript, два React-интерфейса, WebSocket и PostgreSQL 17. Требуются Node.js 24+ и работающий Docker Desktop.

## Запуск в PowerShell

```powershell
Copy-Item .env.example .env
npm.cmd install
npm.cmd run db:up
npm.cmd run db:migrate
npm.cmd run dev
```

Серверный интерфейс: http://127.0.0.1:5173. Клиент: http://127.0.0.1:5174. Backend: ws://127.0.0.1:3000. PostgreSQL доступен только локально на порту 55432: стандартные порты могут использоваться другими проектами. `npm.cmd` позволяет работать без изменения политики выполнения PowerShell.

В серверном интерфейсе заполните логин, пароль и Telegram-логин, сгенерируйте RSA и добавьте пользователя. В клиенте войдите с этими учётными данными. Telegram-логин — текстовое поле, интеграции с Telegram нет. Логины регистрозависимы, пробелы по краям логина удаляются. Пароли не нормализуются.

## Устройство

Пошаговый разбор входа от создания пользователя до выхода: [Полный цикл аутентификации](AUTHENTICATION.md).

Подробный разбор кода, схемы обмена, формулы, таблицы БД и журналов: [Как устроена система](ARCHITECTURE.md).

- `apps/backend`: WebSocket-сервер, проверка входных данных, PostgreSQL и версионируемые SQL-миграции в `src/database/migrations.ts`.
- `apps/server-ui` и `apps/client`: независимые React-приложения.
- `packages/shared` и `packages/ui`: типы протокола, транспорт с переподключением и оформление.

Пароль хранится как SHA-256 от UTF-8 строки без соли по требованиям задания. Это учебная схема хранения. Открытый пароль и его хеш не выводятся в журналы. RSA-2048 генерируется средствами Node.js с e=65537. Параметры p, q, n, φ(n), e, d хранятся десятичными строками и видны только в интерфейсе сервера. Проверка d использует модуль lcm(p−1,q−1), принятый для реальных RSA-ключей. RSA не применяется к авторизации или шифрованию сообщений.

### Двухэтапный вход

1. Клиент отправляет `auth.challenge` с `{login}`. Сервер получает или генерирует `t`: 16 случайных байтов (128 бит). Значение хранится в PostgreSQL и повторно используется для этого пользователя ровно 24 часа, включая переподключения и перезапуски backend. При следующем запросе после истечения срока создаётся новое значение.
2. Сервер возвращает `{challengeHash, expiresAt}`, где `challengeHash = SHA-256(t)` от исходных байтов, а `expiresAt` — дата ISO. Клиент открывает поле пароля.
3. Клиент через Web Crypto вычисляет `H = SHA-256(SHA-256(пароль) + challengeHash)` и отправляет `auth.login` с `{proof: H}`. Оба внутренних хеша — lowercase hex длиной 64 символа; `+` — склейка без разделителя. Внешний SHA-256 вычисляется от UTF-8 этой строки. Пароль при входе не передаётся; для Web Crypto открывайте клиент через localhost, 127.0.0.1 или HTTPS.
4. Сервер вычисляет `H′ = SHA-256(password_hash + challengeHash)` и сравнивает с H через `timingSafeEqual`. Выдача challenge привязана к текущему WebSocket; без неё и после истечения срока вход отклоняется. Неверный пароль не погашает t. Старый формат входа с паролем не поддерживается.

Оба окна показывают журнал этапов, последние 500 записей, с очисткой. `auth.log` содержит `entry` с полями `id`, `attemptId`, `time`, `side`, `step`, `message`. Клиент видит SHA-256(t), H и результат, серверное окно дополнительно t (hex) и H′. Клиентские вычисления записываются локально. Журнал не сохраняется после перезагрузки страницы. Срок t не ограничивает уже авторизованную сессию.

Управление без пароля администратора предназначено для локального использования. Backend привязан к loopback и проверяет Origin. `/ws/admin` поддерживает `rsa.generate`, `users.create`, `users.list`; `/ws/client` — `auth.challenge`, `auth.login`, `auth.me`, `auth.logout`. Запрос: `{id,type,payload}`, ответ: `{id,ok:true,data}` или `{id,ok:false,error:{code,message}}`. Событие обновления списка: `{type:"users.changed"}`. Все операции требуют payload, для операций без параметров — `{}`.

Черновик RSA и сессия живут в пределах соединения; при отключении нужно заново сгенерировать ключи или войти. При тайм-ауте создания проверьте список перед повторной попыткой. Единственный INSERT атомарно сохраняет всю учётную запись. Миграции применяются также при старте backend и защищены блокировкой от одновременного запуска.

## Проверки и остановка

ESLint настроен единым flat config для backend, React-приложений и общих пакетов: рекомендуемые правила JavaScript/TypeScript, правила React Hooks и Fast Refresh. Prettier отвечает за форматирование; `eslint-config-prettier` исключает конфликтующие правила ESLint. Общие настройки: два пробела, одинарные кавычки в JavaScript/TypeScript, точки с запятой, ширина строки 100 и окончания строк LF.

```powershell
npm.cmd run lint
npm.cmd run lint:fix
npm.cmd run format
npm.cmd run format:check
```

`lint` и `format:check` проверяют файлы без изменения и подходят для CI. `lint:fix` исправляет поддерживаемые ESLint ошибки, `format` форматирует проект. Сборки, зависимости, покрытие и служебные файлы браузера исключены; Prettier также пропускает lock-файл и файлы окружения. Для редакторов добавлен `.editorconfig`.

```powershell
npm.cmd run typecheck
npm.cmd run build
npm.cmd test
npm.cmd run db:down
```

Интеграционные тесты требуют запущенной БД, создают отдельную случайную схему и удаляют только её. Обычная остановка Compose сохраняет данные в именованном томе. Не используйте `down -v`, если данные нужны.

Настройки БД задаются в `.env`; при изменении пароля/порта обновите также `DATABASE_URL`. Настройки PostgreSQL инициализируют новый том, но не меняют пароль существующей БД. Vite проксирует `/ws` на порт 3000; при изменении PORT обновите target в обеих Vite-конфигурациях. Сборка интерфейсов предназначена для сервера статики с WebSocket-прокси; README-команды выше запускают локальный режим разработки.
