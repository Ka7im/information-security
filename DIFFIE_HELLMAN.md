# Лабораторная №4 · Диффи — Хеллман с ЭЦП

После входа из лабораторной №3 браузер автоматически запускает обмен. В клиентском окне есть кнопка «Повторить обмен DH». Первый запуск может занять несколько минут: backend асинхронно генерирует безопасное простое p длиной 2048 бит (p = 2q + 1, q простое). Группа с g = 4 переиспользуется до перезапуска backend. Для каждого обмена создаются новые a и b длиной ровно 128 бит.

## Схема реализованного обмена

Если Telegram недоступен, можно отключить его проверку через `TELEGRAM_AUTH_ENABLED=false` в `.env` с перезапуском backend. Тогда предварительный вход выполняется только по паролю; схема DH и проверки RSA-подписей ниже не меняются. Подробнее: [вход без Telegram](README.md#вход-без-telegram).

Сначала общая картина. Стрелка показывает, кто кому отправляет сообщение.

```text
КЛИЕНТ                                      СЕРВЕР
   |                                           |
   |--- Открытый RSA-ключ клиента ------------->|
   |                                           | Вычисляет A = g^a mod p
   |                                           | Подписывает (A, g, p)
   |<-- A, g, p + хеш + подпись сервера --------|
   |    + открытый RSA-ключ сервера             |
   |                                           |
   | Проверяет подпись сервера                  |
   | Вычисляет B = g^b mod p                    |
   | Подписывает B                             |
   |                                           |
   |--- B + хеш + подпись клиента ------------->|
   |                                           | Проверяет подпись клиента
   | K = A^b mod p                             | K = B^a mod p
   |                                           |
   |<-- Хеш серверного K -----------------------|
   | Сравнивает с хешем своего K                |
   |                                           |
   +---------- Получен одинаковый K ------------+
```

**Что означают буквы:**

- `p` — общий простой модуль, `g` — общее основание. Их задаёт сервер.
- `a` — секретное число сервера, `b` — секретное число клиента. Оба по 128 бит и не передаются.
- `A` и `B` — открытые числа, вычисленные из секретных `a` и `b`.
- `K` — общий ключ, который каждая сторона вычисляет самостоятельно.
- Для ЭЦП используется отдельная пара RSA у каждой стороны: `(n, e)` — открытый ключ, `(n, d)` — закрытый. RSA-модуль `n` не является DH-модулем `p`.

### По шагам

**1. Вход.** Клиент проходит существующий вход с паролем и Telegram-кодом. После успеха автоматически запускается обмен DH.

**2. RSA клиента.** Браузер создаёт собственную RSA-пару. Закрытый ключ оставляет у себя, открытый отправляет серверу запросом `dh.init`.

**3. RSA сервера.** Сервер берёт из БД RSA-пару вошедшего пользователя, созданную в первой лабораторной. В этой работе она используется как серверная пара.

**4. Сервер подготавливает AGP и подписывает его.**

```text
Получить p, взять g = 4, создать секретное a.
A = g^a mod p

Сообщение = кортеж (A, g, p)
Хеш = SHA-256(сообщение)
Подпись = Хеш^d mod n          [закрытый RSA-ключ сервера]

Отправить клиенту: A, g, p, хеш, подпись, открытый RSA-ключ сервера.
```

**5. Клиент проверяет подпись сервера.**

```text
Свой хеш = SHA-256(полученный кортеж A, g, p)
Хеш из подписи = Подпись^e mod n   [открытый RSA-ключ сервера]

Свой хеш = переданный хеш = хеш из подписи?
  Да  -> проверить параметры DH и продолжить.
  Нет -> остановить обмен: подпись не прошла проверку.
```

**6. Клиент вычисляет B, свой K и подписывает B.**

```text
Создать секретное b.
B = g^b mod p
Kклиент = A^b mod p

Хеш = SHA-256(B)
Подпись = Хеш^d mod n          [закрытый RSA-ключ клиента]

Отправить серверу: B, хеш, подпись — запрос dh.complete.
```

**7. Сервер проверяет клиента и вычисляет свой K.** Сервер самостоятельно хеширует B и проверяет подпись открытым RSA-ключом клиента — так же, как в шаге 5. Если подпись или параметр B неверны, обмен прекращается. Иначе вычисляется `Kсервер = B^a mod p`.

**8. Сравнение результата.** Сервер отправляет `SHA-256(Kсервер)`. Клиент сравнивает его с `SHA-256(Kклиент)`. При совпадении показывает успешный результат. Сам K по клиентскому соединению не отправляется.

В сообщениях хеш называется `hash`, подпись — `signature`. Дополнительно передаётся `exchangeId`, чтобы сервер связал ответ клиента с текущим обменом. Подробный формат сообщений приведён ниже.

Обе стороны получают одно значение:

```text
Kклиент = A^b mod p = (g^a)^b mod p = g^(ab) mod p
Kсервер = B^a mod p = (g^b)^a mod p = g^(ab) mod p
```

По клиентскому соединению передаются открытые параметры, подписи и хеши. Секретные `a`, `b`, закрытые RSA-ключи и сам `K` в сообщениях `dh.init` / `dh.complete` не передаются. Серверное окно отдельно получает `Kсервер` для учебной демонстрации.

## Ключи RSA

Сервер использует RSA-пару вошедшего пользователя, сохранённую в первой лабораторной. Браузер создаёт собственную, отдельную RSA-2048-пару после входа. Закрытый ключ клиента остаётся в памяти браузера; сервер получает только (n, e). Эта пара используется до выхода или разрыва соединения.

Это учебная ЭЦП без padding: h = SHA-256(сообщение), s = h^d mod n. Получатель самостоятельно вычисляет хеш, сравнивает его с переданным и проверяет s^e mod n = h. Генератор браузера использует Web Crypto для получения RSA-пары; сама учебная подпись вычисляется модульным возведением в степень.

Открытый ключ сервера приходит вместе с параметрами после входа. Схема предполагает доверие к первоначальному соединению и не обеспечивает независимую проверку личности сервера при подмене одновременно ключа и подписи.

## Последовательность

1. Клиент вызывает `dh.init` с `{clientKey: {n, e}}` на авторизованном WebSocket.
2. Сервер выбирает a, вычисляет A = g^a mod p. Подписывает UTF-8 строку `JSON.stringify([A, g, p])`, где все три числа представлены десятичными строками. Возвращает `{exchangeId, A, g, p, hash, signature, serverKey: {n, e}}`.
3. Клиент проверяет подпись и допустимость параметров. Выбирает b, вычисляет B = g^b mod p и Kклиент = A^b mod p.
4. Клиент подписывает UTF-8 десятичной строки B своим закрытым RSA-ключом. Отправляет `dh.complete` с `{exchangeId, B, hash, signature}`.
5. Сервер проверяет подпись закреплённым за обменом открытым ключом клиента, вычисляет Kсервер = B^a mod p и возвращает `{keyHash}`, SHA-256 от UTF-8 десятичной строки K.
6. Клиент сравнивает keyHash с собственным SHA-256(K). При совпадении показывает успешное завершение и локальный K.

Хеши передаются в lowercase hex, большие числа — каноническими десятичными строками. Проверяются длина чисел, диапазоны и принадлежность A и B подгруппе порядка q. Подписанное значение B не содержит идентификатор обмена: это буквальная учебная схема задания, а не полноценный протокол с криптографической привязкой всего диалога.

## Состояние и демонстрация

На соединении разрешён один активный обмен. Повторный запуск очищает предыдущий ключ и параметры. Завершение одноразовое; ошибочная подпись прекращает обмен. Выход, новый вход и отключение очищают состояние. После переподключения нужно войти заново. K не сохраняется в БД и не используется для шифрования дальнейшего трафика в этой работе.

Журналы показывают AGP, B, хеши, подписи и результаты проверки. Клиент показывает свой K локально; сервер отправляет свой K только административным окнам. a, b и закрытый RSA-ключ клиента не передаются. Учебные журналы сохраняют отображённые результаты до очистки или перезагрузки страницы.

Для проверки откройте серверное и клиентское окна, войдите с Telegram-кодом, дождитесь обмена и сравните K в клиентском окне и серверном журнале. Повторный обмен должен дать новый K. Тесты `npm.cmd test` также проверяют подмену параметров и подписей, неправильные ключи, повторное завершение, отмену и обмен через PostgreSQL/WebSocket.

### Общая математика и формат сообщений

Сервер и клиент используют один модуль [packages/shared/src/dh.ts](packages/shared/src/dh.ts), чтобы вычисления и представление подписываемых данных совпадали.

| Функция / тип                                   | Назначение                                                                                                     |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| `modPow(base, exponent, modulus)`               | Быстрое модульное возведение в степень для A, B, K и RSA-подписей.                                             |
| `secret128()`                                   | Криптографически случайный 128-битный показатель; старший бит устанавливается, чтобы длина была ровно 128 бит. |
| `hashText()`                                    | SHA-256 от UTF-8 строки, результат в lowercase hex.                                                            |
| `offerText()`                                   | Однозначная сериализация кортежа: `JSON.stringify([A, g, p])`.                                                 |
| `signText()`                                    | Вычисляет хеш сообщения и подпись `h^d mod n`.                                                                 |
| `verifyText()`                                  | Самостоятельно пересчитывает хеш, сравнивает его с переданным и проверяет `signature^e mod n`.                 |
| `integer()`, `validateRsa()`, `validateShare()` | Проверяют запись чисел, параметры RSA и допустимость открытых параметров DH.                                   |
| `RsaPublicKey`, `SignedHash`, `DhOffer`         | Общие типы открытого ключа, подписи с хешем и предложения сервера.                                             |

В [packages/shared/src/index.ts](packages/shared/src/index.ts), интерфейсе `Operations`, описаны входные и выходные данные `dh.init` и `dh.complete`. Серверные схемы `initPayload` и `completePayload` в [backend/dh.ts](apps/backend/src/auth/dh.ts) проверяют фактические входные сообщения через Zod.
